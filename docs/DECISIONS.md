# Decisions Log

A dated, terse record of significant decisions, pivots, and fixes — the "why," distilled from the full build history in `docs/epics/` and `docs/archive/` so you don't have to read 150 files to understand how the system got here. This file is meant to stay short: one entry per decision, not a rewrite of the original doc. The originals are still in `docs/epics/`/`docs/archive/` if you need the full detail.

**How to add an entry**: one line under the relevant date, past tense, state the decision and the one-sentence reason. If it supersedes an earlier entry, say so instead of leaving both looking current.

---

## Foundation (Epic 1)
- Roles/permissions: three roles (`DINER`/`RESTAURANT_ADMIN`/`PLATFORM_ADMIN`), one per user, no stacking — chosen for simplicity over flexibility since the platform only has three distinct actor types.
- Route protection implemented at both middleware and layout level (defense in depth), not just one or the other.
- API protection (`requireAuth`/`requireRole`) added as a separate layer from page-level guards, so API routes aren't only protected by "the page that calls them happens to be gated."

## Restaurant management (Epic 2)
- Restaurant ownership modeled via `RestaurantMember` (not a direct `ownerId` on `Restaurant`) to support multiple owners/managers per restaurant from the start.
- Media upload: signed direct-to-R2 uploads (not proxied through the Next.js server) to avoid loading server compute/bandwidth with image uploads.
- Restaurant verification/approval workflow (Epic 2.7) added specifically so restaurants can't create dinners before a platform admin reviews them — a quality gate, not just a formality.
- Audit trail (Epic 2.8) added as a cross-cutting concern applied to all admin actions from this point forward, for compliance/accountability, not just debugging.

## Seat lifecycle (Epic 3)
- Centralized seat state machine (Epic 3.9): every status transition goes through one function (`transitionSeatStatus`) instead of ad hoc `prisma.seat.update()` calls scattered across the codebase, specifically so every transition gets the same validation + analytics + audit logging automatically.
- Seat confirmation requires a `SUCCEEDED` `PaymentIntent` (see EPIC_3_SEAT_CONFIRMATION_UPDATE_SUMMARY) — added after the fact to close a gap where seats could be confirmed without payment; this is enforced inside `confirmSeat()` itself, not just at the API boundary, so nothing can bypass it by calling the repository directly.
- **2026-07-18**: found and fixed a real race condition in `holdSeatForDinner()` — the atomic-looking transaction lacked a status-guarded update, so two concurrent requests could both "successfully" hold the same seat (verified empirically: unguarded version let both concurrent holders report success against the same seat; guarded version correctly rejects the loser). Fixed by making `transitionSeatStatus()`'s update a guarded `updateMany` + affected-row check. In the process, removed `SeatStateMachine.holdSeat()` (a separate, correctly-locked-but-never-called implementation) as dead code — its existence had been masking the fact that the real path wasn't actually safe.

## Diner frontend (Epic 4)
- Booking flow built API-first, UI added after — by the time the diner-facing seat confirmation UX (Epic 4.5) shipped, the hold/confirm/payment APIs already existed and were being driven by curl/scripts.
- PWA support + performance polish (Epic 4.8) added manifest/offline handling and Next.js image optimization defaults before public launch, not as an afterthought.

## Post-dinner feedback & trust (Epic 5)
- Feedback flow deliberately branches: a low "comfort level" answer routes into a dedicated safety-flag step; this is a different flow shape than the original wireframes (which had a single always-shown safety screen) — see `docs/STATUS.md` for the current gap analysis against the wireframes.
- Trust score is bounded to a 0–1 range (Epic 5.4) rather than an unbounded counter, so a user can recover from a bad patch rather than being permanently flagged by early history.
- Trust pattern detection (Epic 5.6) flags accounts with 3+ negative signals across 3+ separate dinners — chosen specifically to avoid flagging on a single bad dinner (which could be the other party's fault) while still catching a genuine repeat pattern.

## Theme engine (Epic 6)
- Themes are enabled per-restaurant (`RestaurantEnabledTheme`) rather than global — a restaurant can only create dinners using themes it has explicitly turned on, checked both when populating the dinner-creation form and again server-side when the dinner is actually created (defense in depth, same pattern as auth).
- `DinnerContext`/`ThemePerformance`/`UserThemeSignal` tables added as a forward-looking data-collection layer for theme recommendation/tuning — these are populated but nothing currently reads them yet (no consuming feature built on top).

## Payments (Epic 7)
- Paystack chosen as the payment provider (South Africa focus).
- Webhook-first confirmation, with `/api/payments/verify` as a fallback for the case where the user returns from checkout before the webhook has landed — both paths converge on the same `confirmSeat()` call, so there's one source of truth for "is this seat actually paid for."
- Refund logic added as its own epic (7.4) rather than folded into cancellation, since refund eligibility rules (Paystack-side) are a different concern from the internal cancellation policy.

## Restaurant onboarding (Epic 8)
- Self-service onboarding (sign up → create restaurant → pending approval) chosen over the earlier proposal in `docs/references/CURRENT_AUTH_FRAMEWORK.md` (separate `/sign-up?type=restaurant` flow with role selection at signup) — the simpler "anyone can create a restaurant, it just starts `PENDING`" model shipped instead. `CURRENT_AUTH_FRAMEWORK.md` is now superseded/historical, not a description of the current signup flow.

## Simplification passes
- **2026-03-07/08**: a dedicated simplification pass (`FLOW_SIMPLIFICATION_OPPORTUNITIES.md` → `SIMPLIFICATION_COMPLETE.md`) simplified dinner-discovery filters and the user-sync flow (removed a manual `/sync` redirect step in favor of automatic sync-on-first-authenticated-request).
- **2026-03-14**: booking flow made "atomic" — hold-seat + create-payment-intent combined into a single `/api/bookings/create` call instead of two separate client-driven steps, reducing the window for a client to hold a seat and never follow through with payment initiation.
