## Fixed this session (2026-07-18)

- **Seat-hold race condition**: two concurrent bookings could both "win" the same seat. Fixed with a guarded atomic update; verified empirically against the dev DB (forced-overlap test showed the unguarded version letting both requests succeed, the guarded version correctly rejecting the loser).
- **~20 TypeScript errors**, including two that were real runtime bugs, not just type nits: `/api/seats/[seatId]/confirm` called a method that didn't exist (would 500 on every call — this route has no callers in the app currently, so it hadn't been noticed), and the admin restaurant-approval pages/API were typed without the `user` relation they actually needed.
- **Two of four cron jobs had broken auth**: `expire-holds` and `mark-no-shows` checked a `?token=` query param, but Vercel Cron sends `Authorization: Bearer $CRON_SECRET` — these would have silently 401'd on every real invocation once deployed. Fixed to check the header.
- **Committed credentials**: `.env.example` files contained real-looking Cloudflare R2 keys and a Clerk secret key, committed to a public GitHub repo. Scrubbed from the example files — **rotating the actual keys in the Cloudflare/Clerk dashboards is still on you, this repo fix doesn't undo a prior exposure.**
- **A real circular dependency** between `repositories/`, `services/`, and `utils/` that only worked by accident of module-load order under webpack. Fixed by having `audit-logger.ts` import the repository class directly instead of through the barrel file.
- **Dead code removed**: `SeatStateMachine.holdSeat()` — a correctly-locked implementation that was never actually called by anything, which had been masking the fact that the real hold path wasn't safe.
- **Doc sprawl**: 72 root-level `.md` files + scattered epic/fix docs consolidated into `docs/`. Root now only has `README.md`.
- **`tests/` no longer misrepresents coverage**: it previously held 18 ad hoc `test-*.ts` scripts (manual, console.log-based, never run by vitest) alongside 1 real test. One of those scripts (`test-seat-hold-concurrency.ts`) didn't even call the real booking code — it reimplemented its own separate, also-unguarded hold logic, so it never could have caught the actual race condition. Deleted (superseded by `concurrent-bookings.test.ts`, which does call the real path). `test-state-machine.ts` was converted into a real test with `expect()` assertions (`tests/state-machine.test.ts`). The remaining 15 scripts were moved to `scripts/manual-checks/` and relabeled honestly — `tests/` now contains only files vitest actually runs.
- **Dietary notes now actually reach the database.** The pre-booking textarea's state is lifted into a small client wrapper (`dinner-booking-panel.tsx`, since the page itself is a server component and can't hold state), passed through to `/api/bookings/create`, and persisted on a new `Seat.dietaryNotes` column (migration `20260718125340_add_seat_dietary_notes`). The redundant textarea on the post-booking confirmation page was deliberately left as-is (out of scope, not wired up).
- **Rate limiting extended** to `/api/bookings/create` and `/api/seats/hold` (previously only `/api/payments/create` had it) — same `STRICT` preset, same wrapper pattern. Still in-memory/per-instance (see the gap noted below — this wasn't fixed, just extended to more routes).
- **CSP header added** to `next.config.js`, scoped to what's actually used (Clerk auth domains, Cloudflare Turnstile, R2 image hosts, PostHog) rather than a copy-pasted generic policy. Not yet verified against a live browser sign-in flow — recommended before fully trusting it.
- **New admin platform-ops screens**: `/admin/ops/analytics` (restaurant/dinner counts by status, seat fill rate, revenue, dinner-by-theme breakdown — all computed via database aggregation) and `/admin/ops/users` (list all users, change roles, with a guard preventing a platform admin from demoting themselves out of that role). Both follow the existing defense-in-depth pattern (layout guard + action-level role re-check + audit log + analytics event).
- **A real test-infra gap found and fixed while verifying the above**: `vitest` had no `.env` loading configured — `tests/*.test.ts` construct a `PrismaClient` directly, and unlike the Prisma CLI (which auto-loads `.env`), Prisma Client doesn't. This silently worked in some earlier ad hoc runs but failed outright once tests were re-run from a clean shell. Added `vitest.config.ts` at the repo root to load `.env` before tests run, rather than sprinkling `dotenv` imports into every test file.
- **Mobile responsiveness fixed for the admin surfaces.** The root cause: `admin/layout.tsx` rendered a permanently-visible `w-64` sidebar, leaving ~100px of usable width on a 375px phone screen. Fixed with a new `admin-shell.tsx` client wrapper that turns the sidebar into a hamburger-triggered drawer below `md:`, plus touch-target sizing (`min-h-[44px]` nav links, `py-2.5` form inputs), stacked form action buttons on mobile, and horizontal-scroll wrapping on the filter-tab rows above each admin table. The diner surface (`(core)/`) was spot-checked and confirmed already genuinely mobile-first — no changes needed there.
- **Admin/ops wireframes built and then reskinned**: `wireframes-admin.html` (published as an artifact) first mocked up the 5 core admin/ops screens (restaurant profile, dinner management, ops restaurant-approval, ops analytics, ops users) in the actual slate/dashboard style they're really built in today. Per follow-up request, it was then fully reskinned to the diner app's cream/orange design language (same `--bg:#FAF9F7`/`--p:#FF6B4A` tokens as `wireframes-all-pages.html`, rounded-2xl cards, pill buttons/nav states, soft shadows) — same content and information architecture, different visual skin, as a proposal for what unifying the two surfaces' visual languages would look like. Semantic status colors (pending/active/paused/etc.) were deliberately kept distinct from the orange brand accent rather than reskinned to orange too. This is not yet reflected in the actual admin/restaurant or admin/ops application code — it's a design proposal, not an implemented change.
- **Tech stack reviewed** (Clerk, Prisma, Vercel+Postgres hosting, Paystack) — verdict: keep all four as-is at current scale, no migration recommended. Two concrete side-findings: `apps/web/package.json` declares `@clerk/nextjs: ^5.0.0` while `6.39.1` is what's actually installed/running (stale/wrong manifest entry, worth fixing regardless of the auth-provider question); and the `PaymentProvider.YOCO` enum value has zero actual implementation anywhere (`packages/payment/src/` only has a Paystack client) — it's an unused placeholder, not a partial integration.
- **Fixed `next build` failing at the ESLint step** — ~25 real errors (`@typescript-eslint/no-explicit-any`, unused imports/vars, unescaped JSX entities, a bare `Function` type in `api/lib/middleware.ts`) across ~20 files. All fixed with real types/cleanup, not suppressions — no `eslint.ignoreDuringBuilds` was added. One follow-on type error surfaced once the lint errors cleared (`next build`'s full compile is stricter than `tsc --noEmit` alone) — an unguarded array-index access in `middleware.ts` that could be `undefined`; fixed with a fallback.
- **Fixed the refund double-processing race** — `paymentIntentRepository.refundPayment()` now atomically claims the payment intent (guarded `updateMany`, only succeeds if still `SUCCEEDED`) *before* the route calls Paystack's live refund API, instead of claiming after. A concurrent second request now gets a clean 409 rejection instead of both requests reaching Paystack. If the Paystack call itself then fails, a new `revertRefundClaim()` releases the claim back to `SUCCEEDED` so the payment isn't stuck un-refundable. Verified empirically (`tests/refund-race.test.ts`): two concurrent calls against the same payment intent → exactly one succeeds, one gets a clean rejection, final state is correctly `REFUNDED`.

## Known gaps / not yet true, despite what some old docs claim

- **Three seat-transition methods bypass the state machine entirely**: `checkOut`, `markNoShow` (singular), `markLeftEarly` in `seat.repository.ts` call raw `prisma.seat.update()` directly instead of going through `transitionSeatStatus`. Currently dead code (zero callers anywhere), but it's the same shape of landmine as the `SeatStateMachine.holdSeat()` dead code that masked the real hold-path bug — if wired up later without noticing, it'll silently reintroduce an unguarded race.
- **No `.env.example` documents `RESEND_API_KEY`/`EMAIL_FROM`** — without them the email service silently no-ops (returns `{success:false}`, no throw, no visible error anywhere). A fresh deploy configured only from the example files would never send booking confirmations, reminders, or approval notices, and nobody would notice.
- **`dietaryNotes` has no length limit** anywhere (schema is unbounded `TEXT`, no Zod validation, no `maxLength` on the textarea) — not an XSS risk, but someone could stuff arbitrary amounts of text into it.
- **No in-app payment form.** The wireframes show a custom card-entry screen; the actual app redirects to Paystack's hosted checkout. This is a legitimate design choice, not a bug, but it's a real deviation from the original design intent worth being aware of.
- **"Tonight's Menu" is hardcoded placeholder text** ("Seasonal starter," "Chef's signature main," etc.) rather than real per-dinner dish data.
- **"4 people at table" on the My Reservations card is a literal hardcoded string**, not the dinner's actual seat count.
- **Discover page filter chips are mislabeled under the hood** — "Distance" and "Meal Time" chips actually set date filters; there is no real distance/proximity filter.
- **Rate limiting is still in-memory/per-server-instance**, which doesn't hold under Vercel's serverless auto-scaling — fine as a stopgap, not a real production control at scale. It now at least covers the three endpoints that matter most (payments, bookings, seat-hold).
- **CSP header's Clerk-related directives haven't been verified against a live browser** — recommend loading `/sign-in` with devtools open before fully trusting it.
- **`expire-holds` cron runs every minute** (`* * * * *` in `vercel.json`) — Vercel's Hobby tier doesn't support minute-level cron (Pro-plan only). If deployed on Hobby, this job silently never fires as configured; the booking flow's lazy-reclaim-on-read fallback likely masks this, which is probably why it hasn't been noticed.
- **Post-dinner feedback flow has drifted from the original wireframes**: no star rating, no "vibe tag" selection, no free-text comment on the sentiment step; an extra "Comfort" step was added that wasn't in the original design; and it uses a different color system (gray/blue) than the rest of the app (cream/orange).
- **No animation/interaction library** (`framer-motion`/`motion` absent from `apps/web/package.json`) and **no shared component primitive layer** (`DineButton`/`DineCard`-style components) — both are the concrete reasons the app's UI polish lags behind a more interaction-rich reference design; bounded work to close, not a rewrite.
- **Admin reskin is in progress, not finished.** A shared UI layer now exists (`apps/web/src/components/ui/`: `Button`, `Card` — promoted from the pre-existing `(core)/components/card.tsx`, no duplicate — `Tabs`, `Badge`), and the admin shell (`admin-shell.tsx`/`admin-sidebar.tsx`/`admin-header.tsx`) has been reskinned to the cream/orange palette using it. The individual screens (`admin/restaurant`, `admin/dinners`, `admin/ops/*`) still render in the old slate palette — only the shell wrapping them has changed so far.
