Needs Attention's ⚠/💰 emoji swapped for the icon sprite this pass — this is the one page in the whole file that mixed raw emoji into a screen otherwise built entirely on the custom SVG sprite (i-calendar, i-alert, i-document, etc. throughout the rest of Dashboard alone). Restaurant Onboarding — /admin/restaurant (no restaurant yet)

Restructured into a real 4-step wizard — Basic Info → Location & Contact → Verification → Review & Submit — matching the diner onboarding's own 4-step count. Step 3 (Verification) is new this pass, closing a real spam/trust gap: previously nothing here helped Platform Ops tell a genuine applicant from a spam one before the manual review stage. It collects a Business Registration Number (instant, checkable before any human looks at it) and the compliance document highest in anti-spam value upfront — Food Safety Certificate and Liquor License stay deferred to post-approval, since those often lag a few days behind even a legitimate new restaurant's paperwork; requiring them at signup would reject real applicants along with spam. Real-code note: today's shipped code (admin/restaurant/page.tsx, RestaurantForm mode="create") is genuinely a single-page form with none of this — this entire 4-step wizard, including Step 3's fields, is a recommended upgrade requiring new Restaurant columns (see Implementation Guide §2.1) and is not what currently ships. Sidebar fixed this pass: all 4 steps previously showed "Restaurant Profile" as the active nav item — the same identity as the permanent, ongoing settings page a restaurant returns to for years, worn by a one-time first-run wizard. It's now its own distinct "Onboarding" nav item (different icon, different visual treatment), with every other nav item visibly disabled since there's genuinely nothing behind them yet — no `Restaurant` row means no dinners, no guests, no payouts to show. This item exists only pre-submission; once `createRestaurant()` fires (Step 4), it disappears for good and "Restaurant Profile" resumes its normal place — see Restaurant Profile Editing below, which was untouched by this fix and still shows the standard 5-item sidebar.

Restructured this pass: Overview and Edit are now two separate modes, not one always-open form. Overview (both breakpoints, what you land on by default) is a clean, read-only summary — the same posture as viewing any other business profile in this app. Edit is a deliberate, separate destination reached only via the "Edit Profile" button, which is exactly the surface a permissions check should gate later: Owner and Manager can both reach it today (the only two roles that exist, §sec-team), but hiding one button removes access to every editable field on this page at once, rather than needing a scattered check on a dozen separate inputs. The same reasoning already applies to Team's Remove action and Payouts' bank-detail changes, both already sitting behind their own confirmation modals (§sec-action-modals) — this pass just makes the pattern explicit and named here for the first time. Header consolidated: cuisine tags and the Dinners/Rating/Team stats now share one row instead of two separately-bordered sections (the Team stat's own history is a small story in itself — dropped in an earlier pass as redundant with a Team tab, restored again once that tab was removed and Team became genuinely inline content, see the frame-note below). "Partner Since" demoted to a small caption under the restaurant name, since it's context you'd read once, not a number you'd ever click through on. Edit mode drops the rich banner header entirely — you're mid-edit, not browsing, matching how Meal Editor and Edit Dinner also strip their chrome down to just the form and a Save.
Two more fixes, on direct feedback. Email added to Contact Information (both modes, both breakpoints) — a genuine schema gap, not an oversight in this wireframe alone: Restaurant has phone and website but no business-level email column today (only individual Team members have personal login emails, a different thing). Needs a new Restaurant.contactEmail field — see Implementation Guide §2.1. Overview consolidated further: Business Details, Contact Information, and Operating Hours were three separately bordered-and-shadowed cards stacked for what's really one continuous "about the business" read — closer to a settings form than a calm profile. Merged into one card with quiet section dividers instead, the same grouped-list treatment iOS Settings uses for exactly this kind of read-only fact cluster; Table Themes and Compliance Documents stay separate since they're operationally distinct (a preference and a set of files, not identity facts). Compliance Documents in Overview also drops the ".pdf"-style file extensions — the exact filename only matters when you're about to act on it (delete, re-upload), so it stays in Edit mode only.
Two more fixes this pass, both on the Edit form specifically. Mobile Business Details now has field parity with desktop — Restaurant Name, Cuisine Type, and Address were missing from the mobile Edit form entirely (only Description and City were reachable from a phone), with no note explaining the gap; a restaurant admin genuinely couldn't rename their own restaurant or change its cuisine tags from mobile as previously drawn. All 5 fields now appear on both breakpoints. Operating Hours' standalone "Save Hours" button is gone — desktop used to run two save models on one page (a dedicated Save Hours button plus the page-level Save Changes at the bottom, with no explanation of whether Hours committed independently), while mobile only ever had the single Save Changes bar. Operating Hours is now swept into the one page-level save on both breakpoints, matching mobile's already-correct model instead of mobile matching desktop's more complicated one.
Cancel-button rule, stated explicitly this pass: this form used to show both a "Cancel" button next to Save Changes AND a working back-chevron above it — two exits for the same one action, and genuinely inconsistent with Edit Dinner's own equivalent form (§6.5), which already dropped its Cancel button on the grounds that "the breadcrumb/back-chevron is already the way out." Restaurant Profile Edit's own back-chevron does exactly the same job, so the redundant Cancel button is gone here too, on both breakpoints — one rule, applied the same way on every full-page edit form reached via its own back-chevron. New page — the platform-ops side of the payment-model decision (Implementation Guide §16.5): diners prepay a restaurant-set minimum through the platform, the platform holds those funds, and pays restaurants their net share (minimum − commission) a few business days after each dinner, once the refund/dispute window closes. Recommended v1 approach: no automatic Paystack Split at transaction time — collect the full amount into the platform's own account, then run payouts here as a deliberate batch (even manually-triggered at first, before automating with Paystack's Transfers API once volume justifies it). This keeps refunds trivial (money never left the platform) and avoids clawing funds back from a restaurant's bank account.
